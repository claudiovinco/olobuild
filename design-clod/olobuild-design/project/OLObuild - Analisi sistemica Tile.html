Lettura del sistema di 240 componenti tile e dei relativi config di editing. Non un redesign 1:1, ma i pattern trasversali che si ripetono ovunque — coerenza di brand, default, architettura, accessibilità — con le correzioni da standardizzare una volta sola.

240 tile campione letto: Button · Alert · Hero · Divider + button.js, _styleFieldsBase.js 8 problemi sistemici

Anatomia attuale

Come è fatta e come si modifica una tile, oggi.

Lato render — *Tile.vue

Riceve settings, calcola gli stili in computed, renderizza con un mix di utility mb-* + grossi oggetti :style inline.

I default sono dichiarati dentro il componente.

Lato editor — config/elements

Ogni tipo definisce defaults, fields[] (contenuto) e styleFields[] (stile) su una base condivisa styleFieldsBase().

Lo split Contenuto / Stile / Avanzate è una buona regola universale già presente.

Da preservare ✓

Split semantico, field dichiarativi, helper withHover() e responsive, integrazione FieldBox/box-stack, preset stilistici.

Da sistemare

Default off-brand e duplicati, parsing ripetuto, due linguaggi di stile, emoji, gap di accessibilità, sistemi di editing paralleli (bg/bordo).

Gli 8 problemi sistemici

In ordine di impatto. Ognuno si risolve una volta e vale per tutte le tile.

01Default off-brand, non centrati sui token brandrender

Il token --olo-color-primary esiste, ma i fallback non lo usano in modo coerente: Hero è token-first, Button hardcoda l'indaco. Le tile appena inserite sembrano indaco, non del brand.

✗ ButtonTile.vue
// fallback hardcoded
bg_color: '#6366F1',
backgroundColor: s.bg_color || '#6366F1'
✓ token-first
backgroundColor: resolveColor(
  s.bg_color, TOKENS.primary
) // var(--olo-color-primary,#e1474f)
→
resolveColor(userVal, TOKEN) token-first ovunque. Vedi oloTileDefaults.js.
02Default non "belli appena inseriti" estetica

I default sono validi ma generici: radius 6, padding arbitrari per tile, shadow:'none'. Inserire una tile dovrebbe dare subito qualcosa di curato — è una richiesta esplicita.

✗ generico
border_radius: '6',
shadow: 'none',
tile_padding:{top:14,right:32…}
✓ curato su scala
border_radius: RADIUS.md, // 10
shadow: 'sm', // micro-ombra
tile_padding: SPACE-based
→
TILE_DEFAULTS curati su scala condivisa SPACE/RADIUS, colore brand, contrasto leggibile.
03Default duplicati in due posti — e divergenti editorrender

Stessa proprietà dichiarata sia nel config sia nel componente, con valori che non concordano: fonte di verità ambigua, bug latenti.

✗ due fonti
// button.js
bg_color: ''
// ButtonTile.vue
bg_color: '#6366F1'
✓ fonte unica
// entrambi leggono
buildDefaults('button')
→
Unica fonte dei default (buildDefaults(type)); il Tile non li ridichiara.
04Parsing box-model ripetuto in ogni tile render · DRY

border_radius numero|oggetto e tile_padding oggetto|legacy padding_x/y vengono ri-parsati a mano in Button, Hero (radiusCss), StyleBoxStack… È il gemello lato render di ciò che FieldBox ha già unificato lato input.

✗ copiato N volte
if(typeof rad==='object'){
  borderRadius=`${rad.tl}px …`
}else borderRadius=`${rad||6}px`
✓ composable
const {radiusCss,paddingCss}
  = useBoxModel(s)
→
useBoxModel(settings) + toRadiusCss/toSpacingCss. Vedi useBoxModel.js.
05Due linguaggi di stile mescolati render

Utility mb-* + :style inline giganti + perfino style="…" statici nello stesso template (es. Hero). Difficile da temizzare e tenere coerente.

→
Convergere su un layer (utility, o CSS scoped con var dei token) ed estrarre gli oggetti stile ripetuti in composable.
06Icone emoji come default branda11y

Alert usa ℹ️ ✅ ⚠️ ❌; Divider accetta emoji libere. Resa incoerente tra OS, non accessibile, "cheap" — mentre esiste già il set iconsSvg.

→
Default su icone SVG del set (icon:'info'…); emoji solo come scelta esplicita dell'utente.
07Accessibilità del render a11yrender

Button e le CTA di Hero sono <span> con cursor:pointer — niente focus da tastiera, niente ruolo/semantica, l'URL non è un vero link. Il dismiss dell'Alert non ha label. Nessun controllo di contrasto sui colori custom.

✗ non semantico
<span style="cursor:pointer">
  {{ text }}
</span>
✓ semantico + a11y
<a :href="url"
   role="button"
   :aria-label="text">
→
Elementi semantici nel front-end, aria-label sui controlli icona, avviso contrasto AA nell'editor quando i colori falliscono.
08Editor: concetti duplicati e tab lunghi editor · UX

Button espone sia bg_color sia bg, sia bordo legacy sia oggetto border: due sistemi paralleli, l'utente non sa quale vince. L'hover è sparso su tanti hover_* e l'ombra custom apre 7 campi condizionali inline.

→
Un solo sistema per concetto (preferire gli oggetti bg/border/shadow-block), deprecare i gemelli legacy dietro un layer di migrazione; raccogliere l'hover in un unico modello come fa già StyleBoxStack col toggle Normale/Hover.
