The cache that lied to us for three months

by Devin Cho · 14 min read · updated 2 days ago

It started, as these things do, with a graph that looked too good. Our p99 read latency had dropped off a cliff in March and stayed there. We congratulated ourselves on the new caching layer and moved on. We should not have moved on.

The symptom

Three months later, support started seeing reports of users seeing old data — profile changes that "didn't save", settings that reverted. Intermittent, unreproducible, maddening. The writes were succeeding. The reads were just… wrong.

The cache wasn't slow. It was confident. And it was confidently serving stale values because of a single line:

// cache.ts — the line that cost us a quarter
const ttl = process.env.CACHE_TTL ?? 86400;  // seconds
// CACHE_TTL was unset in prod → 24h TTL, never invalidated on write

The fix, and the lesson

The fix was trivial: invalidate on write, and fail loudly when a config the system depends on is missing. The lesson was not. A metric that only ever looks good is not a metric — it's a blind spot with a dashboard.

We now treat "suspiciously good" the same way we treat "suspiciously bad": as something to investigate before we trust it.
